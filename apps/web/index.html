mizan

Every badge mizan shows is computed by strict normalised containment against a committed corpus, not asserted by a model. The three lines below are the only verdicts the verifier can emit; there is no fourth state and no default badge.

transcript PRECOMPUTED (deterministic replay) the answers and quotations are replayed from a committed transcript; every badge below was computed by the verifier against the committed corpus on this run, live or replayed alike.

The three badges

  • VERIFIED the quoted span is contained in the record the claim cites, after deterministic folding.
  • UNVERIFIABLE mizan cannot decide: no citation, an unresolvable identifier, an empty quote, a paraphrase, a timeout or malformed model output.
  • REJECTED the citation resolved to a real record and that record does not contain the quote.

How a badge is computed

Per claim, in order. Each step fails closed and returns early; the happy path is the last line. The procedure lives in packages/mizan-verify/src/verify.ts and is summarised in the repository README.

  • 1 — the quote. An empty or diacritics-only quoted span is UNVERIFIABLE. Only a quoted span is falsifiable; the model's prose is never verified.
  • 2 — a citation. A claim with none is UNVERIFIABLE. Zero evidence blocks approval.
  • 3 — the cap. More than three citations are capped; the cap becomes the recorded reason only when it is the reason.
  • 4 — resolution. If no cited record exists the claim is UNVERIFIABLE; a number that exists in several collections with none named is UNVERIFIABLE as ambiguous.
  • 5 — containment. The folded quote is compared to the folded cited record by strict normalised substring containment. A hit is VERIFIED, with evidence. This is the only route to VERIFIED in the repository.
  • 6 — coercion. A VERIFIED carrying no evidence is coerced down to UNVERIFIABLE, and the evidence is cleared so nothing downstream can render a confident badge with no provenance.

Between containment and accusation sits the anchor arm: an abridgement that a hand-drawn anchor locates in the cited record yields UNVERIFIABLE — never VERIFIED and never REJECTED. A case nobody ruled on receives no anchor and falls back to the containment result.

What the fold is

One table, in packages/mizan-core/src/normalize/fold-table.ts, applied once at ingest. It normalises alef and hamza forms, the wasla, ta-marbuta, diacritics, tatweel, digit forms and punctuation. It never rewrites, adds or removes a letter — which is exactly why a fabrication cannot be folded into a match.

The folded column is a matching key, not a text. Every user surface renders the original; only the verifier compares the key.

Match strength is exact or none

Every verdict carries one of two match strengths: exact (a containment hit) or none. There is no percentage on any verdict and no third shape. A display-only longest-run diagnostic exists for human reading; it is not a verdict, and the verifier cannot import it.

Grades are never ours

A grade is stored exactly as the source dataset asserts it, together with who published it and on what basis. Rows the dataset declines to grade carry an explicit “no grade” state rather than a default. The product never infers, upgrades or presents a grade as its own ruling.

Qur'an rows from Tanzil carry no hadith grade at all. Hadith rows from QuranLab carry the dataset's own per-row grade; the reference/isnad payload is not ingested.

Honest degradation

Each failure has one correct surface. These are the words the product prints; a different spelling of the same absence is a defect, not a style choice.

  • provider unreachable inside its 30s budget → model unavailable — never a canned answer, never a silent mock.
  • corpus consulted, nothing citable → no sources found — never a guess, never a cached answer.
  • verification timeout or malformed model output → unverifiable — never verified, never a cached prior verdict.
  • attestation mismatch or ledger write failure → loud integrity error, no verdict — never warn-and-proceed.
  • corpus absent or unreadable → the pipeline is not entered; the CLI names the state and exits.
  • not every claim verified → the run action is refer_to_scholar, not a composite yes.

Second-ranker absence is reported in run metadata as semanticRanking: unavailable, never as a silent downgrade presented as full fidelity.

Provenance you can check

  • The corpus snapshot is attested; a mismatch between the database and its attestation aborts the run rather than producing a badge.
  • Every ledger row is hash-chained — each row carries the hash of the row before it. bun run verify:chain re-checks the chain from the committed file.
  • Run traces carry a hash of the question, never the question text.
  • Every badge is computed against a snapshot whose hash is shown beside it in the CLI report and in the hosted demo.

Evaluated on cases that must fail

Two committed eval sets, both hand-adjudicated: data/eval/golden-normalization.json (200 cases the fold table must decide correctly) and data/eval/redteam-fabricated.json (40 fabricated citations that must never earn VERIFIED).

The red-team cases cite real collection names with fabricated content, chimeric citations and wrong-venue attributions. Each is published synthetic test data, not hadith, and a test fails if the eval generator ever imports the verifier.

Sources and licences

Corpus text is not covered by the code's Apache-2.0 licence. Per-source terms live in data/registry/sources.json, and gate G-5 fails the build on an empty licence field.

  • Tanzil Project — Qur'an, Uthmani script, 6,236 records. Distributed unmodified under the Tanzil terms of use (no-derivatives class in the registry).
  • QuranLab — hadith and per-row grades, 36,024 records ingested. Arabic matn public domain per the dataset card. Grades stored exactly as published.

Served collections in this snapshot: the Qur'an, Sunan Abi Dawud, Sunan an-Nasa'i, Sunan Ibn Majah, Jami' at-Tirmidhi, and Malik's Muwatta — 27,234 rows, as recorded in docs/value-proof.md. Bukhari, Muslim and an-Nawawi are not served; the registry and the eval tables say so rather than implying a wider coverage than the snapshot holds. Rows the dataset declines to grade are held back rather than served with an invented grade.

Where to run it

  • bun run demo — the offline demonstration. No API key, labelled replay, full report with each source's URL and the snapshot hash beside every badge. About a second on a laptop.
  • bun run ask — the CLI question path. With a key set in the environment it runs the live model against an allowlisted OpenAI-compatible endpoint; without one it replays the committed transcript and labels every line precomputed.
  • bun run demo-server — the hosted-form demo. Server-rendered HTML, no client-side script: an ask form, a verify playground, and GET /health for the platform. Badges are computed in the server process.
  • bun run mcp — mizan verification as a read-only MCP tool (server name mizan-verify) for other AI applications, over stdio.
  • bun run ci — typecheck, per-package tests, then the structural gates G-1 through G-7.

The repository is at github.com/mossaudi/mizan. Deployment notes for the static exhibit and the hosted demo are in docs/live-demo.md; the offline command walkthrough is docs/demo-runbook.md.

This page makes no request, and takes no input

No script, no stylesheet link, no image, no font, no fetch. It renders from file:// with zero network access, so what you are reading is the committed bytes and nothing else. There is no text box on purpose: accepting input needs a script, and ADR-C3 forbids one. To ask a question, use the CLI — bun run ask, with a key set for a live run and unset for the labelled replay; bun run demo prints the full report, with each source’s URL and the snapshot hash beside every badge. For an interactive form, the hosted demo server (bun run demo-server) serves one from a separate process; this static exhibit stays offline.
